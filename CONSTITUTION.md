# Tavern Constitution

## Preamble

Tavern exists to make my personal way of managing to-dos simple and usable. It is deliberately opinionated: the workflow should conform to how I think and work. Its direction comes from my needs and judgement.

I want to capture work, review it, put it in priority order, and get on with doing it. The inbox and review ideas from GTD are useful for that. The system should keep the work clear and reduce the effort of managing it. Elaborate scheduling and process for its own sake would defeat the reason for building Tavern.

Markdown in an Obsidian vault is a deliberate foundation. Plain text gives me simple primitives, keeps tasks usable by LLMs, and places limits on how complicated the system can become. The plugin makes that foundation easier to use.

## Founding Principles

1. **My workflow sets the direction.** Tavern is personal and deliberately opinionated. Changes should serve how I work. Reject complexity added to accommodate hypothetical users or turn Tavern into a general-purpose task manager.

2. **The Markdown stays clean and stands on its own.** Tasks, project structure, and ordering within notes remain understandable and editable without Tavern. Changes made through the UI are reflected in those notes. Reject features that make the Markdown harder to read or require the plugin to interpret its meaning.

3. **Tavern adds convenience, with state of its own.** Global views, the focus queue, and prioritisation tools such as an Eisenhower matrix are UI/UX sugar. Their state may belong to the plugin. This convenience state is distinct from the underlying task and project content; neither needs to be forced into the other’s storage.

4. **Line up the work and do it.** Work is organised by priority, expressed through order. Tavern does not track dates, deadlines, or scheduled work. Reject calendar-driven task management, even when a task has a genuine deadline.

5. **Use a method only as far as it helps.** GTD’s inbox and review are useful; following an entire methodology is not a goal. Simple reusable checklists are welcome. Reject complicated workflows, unnecessary views, and recurrence machinery that creates fresh tasks to administer.

## Growth Directives

1. **Toward smoother everyday task management.** Improve the UI/UX shell over the task and project data so capturing, arranging, reviewing, and completing work takes less effort.

2. **Toward clarity without clutter.** Make richer management tools available when useful, while keeping everyday work simple and focused.

3. **Toward more useful ways to work with independent data.** Evolve the plugin’s views and interactions within its role as a convenience layer. UI state belongs to Tavern; task and project data stays independently readable and editable.

## Boundaries

1. **Do not become a configurable workflow platform.** Tavern has one opinionated workflow encoded in its code. Reject generic abstractions and customisation systems intended to let people construct different workflows.

2. **Do not expand beyond the intended scope.** Do not pursue feature parity with other task or project management products. Functionality must be planned or requested, consistent with Tavern’s principles, and limited to what the intended workflow needs.

3. **Do not make task and project data depend on Tavern.** It must remain clean, understandable, and editable through the Markdown itself. UI state may belong to the plugin.

4. **Do not become a calendar or scheduling system.** Tavern does not track task dates, deadlines, or scheduled work.

## Tension Pairs

1. **Useful capability over the smallest feature count — but never at the cost of focus.** Include functionality where it serves the intended workflow. Keep it out of other contexts where it adds no value.

2. **Continuity over perfect UI precision — but never at the cost of easy correction.** Prefer preserving working context through reversible UI choices, even if I need to tidy it afterward. Uncertainty should not automatically discard work I had selected.

3. **Plugin-owned UI state over forcing every convenience into Markdown — but never at the cost of independent task and project data.** Views and prioritisation tools may maintain their own state. Changes to the underlying tasks and projects still belong in the notes.
